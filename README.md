# bufpool

Memory pool for programs that allocate a lot of similar-sized buffers and have a hard memory limit (think a video player on a cheap TV box). Wanted to see if a simple size-class pool with a "give pages back to the OS" policy actually beats malloc for this.

Short answer: not on speed or peak memory, but yes on giving memory back.

## how it works

- power of two size classes, 256 B to 1 MB. anything bigger gets its own mmap
- small classes are carved out of 2 MB arenas (2 MB aligned so pointer -> arena is just a shift + table lookup)
- hard budget: if an allocation would go over, it trims free pages first, then returns nullptr. process never grows past the limit
- 3 policies for returning memory with `madvise(MADV_DONTNEED)`: immediately, once free memory passes a threshold, or never
- one mutex per size class
- debug mode poisons freed memory and catches double frees

bookkeeping is kept outside the arenas on purpose, since MADV_DONTNEED zeroes the pages and would wipe an in-place free list.

```cpp
bufpool::Config cfg;
cfg.budget_bytes = 64 << 20;
bufpool::Pool pool(cfg);

void* p = pool.Allocate(512 * 1024);  // nullptr if over budget
pool.Free(p);
```

## build

```
cmake -S . -B build
cmake --build build -j
ctest --test-dir build
```

`-DBUFPOOL_SANITIZE=address` or `thread` if you want sanitizers (CI runs both).

## benchmark

`bufpool_bench` replays allocation traces against malloc and each policy, each run in its own forked process, and reads RSS from `/proc/self/statm`.

The steady/seeky/abr traces are generated by `bench/gen_trace.py` (fake player heap, 10 min). The two tinyplayer ones are recorded from my [tinyplayer](https://github.com/Pranay7ej/tinyplayer) project with `--alloc-trace`.

```
./build/bufpool_bench bench/traces/*.txt
```

Numbers from a 2 core VM, no budget:

| trace | allocator | ns/op | peak RSS MB | RSS after free MB |
|---|---|---:|---:|---:|
| steady | malloc | 178 | 15.9 | 15.9 |
| steady | pool/immediate | 4388 | 17.6 | 0.7 |
| steady | pool/threshold | 205 | 20.6 | 0.7 |
| steady | pool/never | 177 | 20.6 | 20.6 |
| seeky | malloc | 164 | 14.4 | 9.4 |
| seeky | pool/threshold | 250 | 16.9 | 2.0 |
| abr | malloc | 222 | 36.2 | 28.4 |
| abr | pool/immediate | 5872 | 35.5 | 1.1 |
| abr | pool/threshold | 341 | 40.9 | 6.3 |
| abr | pool/never | 162 | 60.4 | 60.4 |
| tinyplayer_drop | malloc | 4071 | 13.6 | 3.1 |
| tinyplayer_drop | pool/threshold | 14861 | 20.9 | 7.9 |

Things I noticed:
- peak memory is worse than malloc because of power of two rounding (10 KB packet -> 16 KB slot). finer classes would fix most of that
- the win is after the burst: malloc still holds 9-28 MB, pool with a return policy drops to ~1 MB
- returning immediately is way too slow (a madvise per free). threshold is the sweet spot
- "never" is bad when sizes change (abr trace), every quality you played stays resident
- the tinyplayer traces are all multi-MB segments and glibc already handles those fine with mmap. if I used this in the player I'd only pool the small stuff
